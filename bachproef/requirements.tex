\chapter{\IfLanguageName{dutch}{Requirementsanalyse}{Requirementsanalyse}}%
\label{ch:requirementsanalyse}

Deze requirementsanalyse beschrijft de functionele en niet-functionele vereisten van DepGuard AI, de AI-gestuurde dependencydashboardoplossing die in deze bachelorproef wordt ontwikkeld. De analyse bouwt voort op de probleemstelling, literatuurstudie en het overleg met de co-promotor. Het platform wordt opgezet als een losstaande webapplicatie, onafhankelijk van bestaande tools zoals Dependabot, en richt zich op het samenvatten van release notes, het beoordelen van de kriticiteit van updates en het ondersteunen van het kernteam bij het prioriteren van dependency updates.

\section{Stakeholders}
\label{sec:stakeholders}

De belangrijkste stakeholders van DepGuard AI zijn:

\begin{itemize}
  \item \textbf{Kernteam voor platform- en dependencybeheer}: primaire gebruikers, verantwoordelijk voor het opvolgen en doorvoeren van dependency-updates en dagelijks gebruik van het dashboard voor overzicht, prioritering en AI samenvattingen.
  \item \textbf{Developers binnen projecten}: secundaire gebruikers die aan individuele projecten werken, update-adviezen raadplegen en projectleden en dependencies beheren.
  \item \textbf{Co-promotor / bedrijfsbegeleider}: opdrachtgever vanuit Springbok, die de bruikbaarheid en kwaliteit van de oplossing evalueert en mee de requirements scherpstelt.
  \item \textbf{Promotor (HOGENT)}: academische begeleider die de methodologie, uitvoering en kwaliteit van het eindwerk beoordeelt.
  \item \textbf{Externe platforms}: GitHub en de npm-registry leveren project- en versiemetadata via hun APIs en vormen zo cruciale bronnen voor het systeem.
\end{itemize}

\section{Functionele vereisten}
\label{sec:functionele-vereisten}

De functionele vereisten zijn gegroepeerd per domein en geprioriteerd volgens de MoSCoW-methode (Must Have, Should Have, Won't Have voor dit proof-of-concept).

\subsection{Authenticatie en gebruikersbeheer}
\label{sec:auth-gebruikersbeheer}

De volgende functionele vereisten gelden voor authenticatie en gebruikersbeheer.

\begin{itemize}
  \item \textbf{F-01 (Must Have)}: Gebruikersregistratie en login via e-mail en wachtwoord (Supabase Auth).
  \item \textbf{F-02 (Must Have)}: Aanmaken van een bedrijfsaccount (multi-tenant).
  \item \textbf{F-03 (Must Have)}: Uitnodigen van teamleden via e-mail met rolkoppeling (Resend API).
  \item \textbf{F-04 (Must Have)}: Rollen per bedrijf: owner, project\_lead, developer, tester (RBAC).
  \item \textbf{F-05 (Must Have)}: Rollen per project: project\_lead, developer (projectniveau RBAC).
  \item \textbf{F-06 (Should Have)}: Uitnodiging accepteren via directe link zonder e-mail (fallbackflow).
  \item \textbf{F-07 (Could Have)}: SSO / OAuth login (bijvoorbeeld GitHub of Google via Supabase OAuth).
\end{itemize}


\subsection{Projectbeheer}
\label{sec:projectbeheer}

De volgende functionele vereisten gelden voor projectbeheer.

\begin{itemize}
  \item \textbf{F-08 (Must Have)}: Aanmaken, bewerken en verwijderen van projecten (CRUD).
  \item \textbf{F-09 (Must Have)}: Koppelen van een publieke GitHub-repository aan een project (GitHub-integratie).
  \item \textbf{F-10 (Must Have)}: Uploaden van een \texttt{package.json} om dependencies in te laden.
  \item \textbf{F-11 (Must Have)}: Toewijzen van teamleden aan projecten met projectrol.
  \item \textbf{F-12 (Must Have)}: Overzicht van alle projecten per bedrijf met statusindicator.
  \item \textbf{F-13 (Could Have)}: Archiveren of deactiveren van projecten.
\end{itemize}


\subsection{Dependency scanning en versiebeheer}
\label{sec:dependency-scanning}

De volgende functionele vereisten gelden voor dependency scanning en versiebeheer.

\begin{itemize}
  \item \textbf{F-14 (Must Have)}: Automatisch detecteren van dependencies via GitHub (uitlezen van \texttt{package.json} via de GitHub API).
  \item \textbf{F-15 (Must Have)}: Ophalen van de meest recente versie via de npm-registry (\texttt{npmjs.org}).
  \item \textbf{F-16 (Must Have)}: Vergelijken van huidige versie met meest recente versie (semver-vergelijking).
  \item \textbf{F-17 (Must Have)}: Classificeren van updates als major, minor of patch (semver-classificatie).
  \item \textbf{F-18 (Must Have)}: Opslaan van dependency-informatie (naam, versies, status) in Supabase Postgres.
  \item \textbf{F-19 (Should Have)}: Manueel hertriggeren van een scan door de gebruiker.
  \item \textbf{F-20 (Could Have)}: Automatisch periodiek scannen via een geplande job (cron).
  \item \textbf{F-21 (Won't Have)}: Ondersteuning voor meerdere registries (bijv. PyPI, Maven).
\end{itemize}


\subsection{AI-analyse en samenvatting}
\label{sec:ai-analyse}

De volgende functionele vereisten gelden voor AI-analyse en samenvatting.

\begin{itemize}
  \item \textbf{F-22 (Must Have)}: AI-agent analyseert changelogs en release notes van npm en GitHub (Mastra-agent met LLM-backend).
  \item \textbf{F-23 (Must Have)}: Genereren van een begrijpelijke samenvatting per dependency-update.
  \item \textbf{F-24 (Must Have)}: Classificeren van het updatetype: security fix, bugfix, nieuwe feature, breaking change.
  \item \textbf{F-25 (Must Have)}: Aanduiden of een update veilig, risicovol of kritiek lijkt (risico-indicatie).
  \item \textbf{F-26 (Must Have)}: Opslaan van de AI-samenvatting per dependency in het veld \texttt{ai\_summary}.
  \item \textbf{F-27 (Must Have)}: Ondersteuning voor meerdere AI-providers (OpenAI, Google Gemini).
  \item \textbf{F-28 (Should Have)}: Alternatieve AI-workflow via n8n (low-code orkestratie als vergelijking met de Mastra-agent).
  \item \textbf{F-28b (Should Have)}: Alternatieve AI-agent via OpenAI Agent Builder, waarbij een gehoste agent met tools wordt geconfigureerd als tweede alternatief naast Mastra en n8n.
  \item \textbf{F-29 (Should Have)}: Verrijken van AI-input met webcontext via Tavily.
  \item \textbf{F-30 (Should Have)}: Hertriggeren van AI-analyse op verzoek van de gebruiker.
  \item \textbf{F-31 (Could Have)}: Gestructureerde output met migratiestappen en deprecation-warnings.
\end{itemize}


\subsection{Dashboard en visualisatie}
\label{sec:dashboard}

De volgende functionele vereisten gelden voor het dashboard en visualisatie.

\begin{itemize}
  \item \textbf{F-32 (Must Have)}: Overzichtsdashboard met statistieken (verouderde packages, security-issues, recente activiteit).
  \item \textbf{F-33 (Must Have)}: Detailweergave per project met lijst van dependencies en hun status.
  \item \textbf{F-34 (Must Have)}: Weergave van de AI-samenvatting per dependency in het dashboard.
  \item \textbf{F-35 (Must Have)}: Visuele badge of kleurcodering voor major/minor/patch en risico-niveau.
  \item \textbf{F-36 (Should Have)}: Filteren en sorteren van dependencies op status, updatetype en kriticiteit.
  \item \textbf{F-37 (Could Have)}: Exporteren van een dependency-rapport als PDF of CSV.
\end{itemize}


\subsection{Notificaties en communicatie}
\label{sec:notificaties}

De volgende functionele vereisten gelden voor notificaties en communicatie.

\begin{itemize}
  \item \textbf{F-38 (Must Have)}: E-mailnotificatie bij uitnodiging van een nieuw teamlid (Resend API).
  \item \textbf{F-39 (Should Have)}: E-mailnotificatie bij detectie van een kritieke security-update.
  \item \textbf{F-40 (Could Have)}: In-app notificatie of badge bij nieuwe updates per project.
  \item \textbf{F-41 (Won't Have)}: Integratie met Slack of Microsoft Teams voor updateberichten.
\end{itemize}


\subsection{Regels en beslissingsondersteuning}
\label{sec:regels-beslissing}

De volgende functionele vereisten gelden voor regels en beslissingsondersteuning.

\begin{itemize}
  \item \textbf{F-42 (Must Have)}: AI geeft een advies per dependency: ``veilig te updaten'', ``voorzichtigheid geboden'' of ``kritiek''.
  \item \textbf{F-43 (Should Have)}: Mogelijkheid om een dependency handmatig als ``genegeerd'' of ``gedaan'' te markeren.
  \item \textbf{F-44 (Could Have)}: Definiëren van updatebeleid per project (bijvoorbeeld patch-updates automatisch goedkeuren).
  \item \textbf{F-45 (Won't Have)}: Automatisch aanmaken van pull requests of GitHub-issues op basis van advies.
\end{itemize}


\section{Niet-functionele vereisten}
\label{sec:niet-functionele-vereisten}

De niet-functionele vereisten zijn afgestemd op de gekozen technische stack (Next.js, Supabase, Mastra, n8n, OpenAI-agent builder en externe LLms) en de context van Springbok.

\subsection{Beveiliging}
\label{sec:nfr-beveiliging}

\begin{itemize}
  \item \textbf{NFR-01}: Row Level Security (RLS) in Supabase zorgt ervoor dat gebruikers uitsluitend data zien van het eigen bedrijf en de toegewezen projecten.
  \item \textbf{NFR-02}: Authenticatie is verplicht voor alle API-routes en dashboardpagina's via Next.js-middleware.
  \item \textbf{NFR-03}: API-sleutels (OpenAI, Google, Resend, GitHub) worden uitsluitend als omgevingsvariabelen opgeslagen en zijn nooit zichtbaar in de frontend.
  \item \textbf{NFR-04}: Uitnodigingstokens zijn eenmalig geldig en vervallen na acceptatie.
\end{itemize}


\subsection{Prestaties}
\label{sec:nfr-prestaties}

\begin{itemize}
  \item \textbf{NFR-05}: De end-to-end AI-analyse (van dependency-input tot opgeslagen samenvatting) wordt onder normale omstandigheden binnen ongeveer 30 seconden afgerond.
  \item \textbf{NFR-06}: Paginalaadtijden voor het dashboard blijven onder 2 seconden bij een dataset tot ongeveer 200 dependencies per bedrijf.
  \item \textbf{NFR-07}: De n8n-workflow en de Mastra-agent worden parallel geëvalueerd op doorlooptijd; de resultaten worden vastgelegd in de evaluatiefase.
\end{itemize}


\subsection{Schaalbaarheid}
\label{sec:nfr-schaalbaarheid}

\begin{itemize}
  \item \textbf{NFR-08}: De multi-tenant architectuur laat toe om meerdere bedrijven, projecten en gebruikers onafhankelijk van elkaar te beheren.
  \item \textbf{NFR-09}: Opslag op Supabase (PostgreSQL) ondersteunt schaalbaarheid via managed infrastructuur en connection pooling.
  \item \textbf{NFR-10}: De AI-agentlaag is modulair en kan worden uitgebreid met extra tools, registries of LLM-providers zonder ingrijpende wijzigingen aan de webapplicatie.
\end{itemize}


\subsection{Betrouwbaarheid en foutafhandeling}
\label{sec:nfr-betrouwbaarheid}

\begin{itemize}
  \item \textbf{NFR-11}: Bij het ontbreken van release notes in GitHub wordt teruggevallen op bestanden zoals \texttt{CHANGELOG.md}, \texttt{CHANGES.md} of \texttt{HISTORY.md}.
  \item \textbf{NFR-12}: Als er geen changelog-informatie beschikbaar is, vermeldt de AI-agent dit expliciet in de samenvatting.
  \item \textbf{NFR-13}: API-fouten (GitHub, npm, LLM) worden gelogd en weergegeven als leesbare foutmeldingen in de UI.
  \item \textbf{NFR-14}: De Mastra-server en de Next.js-applicatie zijn onafhankelijk startbaar; bij uitval van Mastra blijft het dashboard bruikbaar zonder AI-analyse.
\end{itemize}


\subsection{Onderhoudbaarheid}
\label{sec:nfr-onderhoudbaarheid}

\begin{itemize}
  \item \textbf{NFR-15}: De volledige codebase is getypeerd in TypeScript.
  \item \textbf{NFR-16}: Logica is opgesplitst per verantwoordelijkheid: AI-agentcode, API-routes en UI-componenten zijn in aparte modules gestructureerd.
\end{itemize}


\subsection{Bruikbaarheid}
\label{sec:nfr-bruikbaarheid}

\begin{itemize}
  \item \textbf{NFR-17}: Het dashboard is responsive en bruikbaar op verschillende schermformaten.
  \item \textbf{NFR-18}: AI-samenvattingen zijn geschreven in begrijpelijke taal, gericht op developers zonder diepgaande AI-kennis.
  \item \textbf{NFR-19}: Statusbadges voor updatetype en risiconiveau zijn kleurgecodeerd en direct interpreteerbaar.
  \item \textbf{NFR-20}: Het onboardingproces (registratie, bedrijf aanmaken, project koppelen en eerste scan) kan in minder dan vijf minuten worden doorlopen.
\end{itemize}


\subsection{Traceerbaarheid en audit}
\label{sec:nfr-traceerbaarheid}

\begin{itemize}
  \item \textbf{NFR-21}: Mastra voorziet tracing en logging van agentbeslissingen, tool-calls en modelinteracties, zodat het gedrag van de AI-agent kan worden geanalyseerd.
  \item \textbf{NFR-22}: Alle AI-samenvattingen worden met tijdstempel opgeslagen zodat de evolutie van adviezen per dependency navolgbaar is.
  \item \textbf{NFR-23}: Gebruikersacties zoals scannen, analyseren en uitnodigen zijn via Supabase auditeerbaar.
\end{itemize}


\subsection{Portabiliteit en installatie}
\label{sec:nfr-portabiliteit}

\begin{itemize}
  \item \textbf{NFR-24}: De applicatie kan lokaal worden gestart via \texttt{npm run dev} (Next.js) en \texttt{npm run dev:mastra} (Mastra) na configuratie van de omgevingsvariabelen.
  \item \textbf{NFR-25}: De database-opzet is volledig scriptbaar en vereist geen manuele tabelaanmaak.
  \item \textbf{NFR-26}: De applicatie is inzetbaar op courante cloudplatformen, bijvoorbeeld Vercel voor Next.js en Supabase Cloud voor de databank.
\end{itemize}

\label{sec:moscow-overzicht}
